1. PROPÓSITO DE ESTE ARCHIVO
----------------------------

Este archivo es la fuente de verdad persistente para recordar qué módulos del
proyecto TransPort están desarrollados, cuáles están incompletos y cuáles deben
implementarse después.

Debe actualizarse cuando:

- Se apruebe el inicio de un módulo.
- Cambie el alcance de un módulo.
- Un módulo pase de Pendiente a En desarrollo.
- Se complete y verifique un módulo.
- Se identifique una dependencia o deuda técnica relevante.
- El usuario apruebe o rechace un módulo opcional.

No se marcará un módulo como Implementado solamente porque existan tablas,
pantallas de demostración o tarjetas visuales. Debe existir el flujo funcional
requerido entre MVC, API, lógica/repositorio y SQL Server, junto con una
verificación proporcional al riesgo.


2. FUENTES DE REQUISITOS Y REGLAS DE ALCANCE
--------------------------------------------

El avance debe mantenerse alineado, en este orden, con:

1. Las decisiones explícitas más recientes del usuario.
2. El alcance técnico de "PROMPT PARA CODEX - TRANSPORT / FASE 1".
3. El caso y los requisitos generales de "Proyecto final.pdf".
4. ESTADO_PROYECTO.md, README.md y el código realmente disponible.

Reglas obligatorias:

- El frontend MVC nunca accede directamente a SQL Server.
- Los datos pasan por TransPort.Api.
- La persistencia utiliza ADO.NET y procedimientos almacenados.
- No se agregan microservicios o infraestructura sin necesidad aprobada.
- Los permisos se validan tanto en MVC como en la API.
- Los alcances por rol, giro, sede y cliente deben aplicarse en cada módulo.
- Los módulos futuros no deben mostrar datos falsos como si fueran reales.
- Cualquier módulo no exigido por los requisitos se registra únicamente en la
  última sección "MÓDULOS OPCIONALES" y no se implementa sin decisión del
  usuario.

4. MÓDULOS YA DESARROLLADOS
---------------------------

M01. Base técnica y arquitectura                               [IMPLEMENTADO]

- Solución .NET 8 con TransPort.Web y TransPort.Api.
- MVC y API en proyectos y contenedores separados.
- SQL Server externo y conexión configurable.
- ADO.NET, procedimientos almacenados e inyección de dependencias.
- Organización modular inicial: Seguridad, Organización y Shared.

M02. Base de datos organizacional inicial                      [IMPLEMENTADO]

- Tablas de usuarios, roles, giros, sedes, clientes, relaciones y auditoría.

- Instalador SQL idempotente y datos iniciales.
- Procedimientos almacenados iniciales para usuarios, catálogos, asociaciones,
  clientes, resumen y auditoría.

M03. Seguridad, autenticación y autorización                   [IMPLEMENTADO]

- Login único en /acceso.
- Validación de credenciales mediante procedimiento almacenado.
- JWT firmado y de duración limitada para comunicación MVC-API.
- Cookie HttpOnly y Claims para autenticación del navegador.
- JWT almacenado únicamente en la sesión del servidor MVC.
- Envío Bearer y validación independiente en la API.
- Roles y asociaciones de giro, sede y cliente incluidos en la identidad.
- Acceso denegado, cambio entre portales y cierre completo de sesión.
- Protección antiforgery para formularios MVC que modifican información.

M04. Administración de usuarios                               [IMPLEMENTADO]

- Listar, buscar y filtrar usuarios.

- Activar, desactivar y eliminar lógicamente.
- Asignar y retirar roles, giros y sedes.
- Validaciones y restricciones para proteger la cuenta administradora activa.
- Flujo MVC -> API -> repositorio -> procedimiento almacenado.

M05. Sitio público                                             [IMPLEMENTADO]

8. PENDIENTES TÉCNICOS TRANSVERSALES
------------------------------------

No son módulos comerciales independientes, pero deben atenderse antes de una
puesta en producción o cuando el crecimiento los haga necesarios:

- Diferenciar cancelaciones HTTP normales de errores 500 en el middleware.
- Reemplazar contraseñas en texto plano por hashes seguros antes de usar datos
  reales; el texto plano existe únicamente por la condición académica inicial.
- Agregar HTTPS estricto y administración real de secretos.
- Incorporar health checks y mejor observabilidad.
- Migrar la sesión MVC a Redis o SQL Server Distributed Cache antes de escalar
  horizontalmente el frontend.
- Definir respaldo y alta disponibilidad para SQL Server.
- Aplicar autorización por rol, giro, sede y cliente en cada endpoint futuro.
